## Background

**這件事解的不只是「引擎更準」，是一個動線問題。**

前端 `frontend/src/components/ProcPanel.vue` 有一個「審查結論」下拉，使用者選 A／B／C／D 就直接在**本地**生成決定主文（`docBuilders.js:146-148`）。也就是說：**程序審查的結論目前是使用者挑的，不是系統判的。**

整合之後，**A（程序不合 → 不受理）由引擎判定**，前端不再需要讓人挑那一格。

### 已驗證的能力（不是宣稱，是量過的）

| 模組 | 對應 | 驗證 |
|---|---|---|
| `overdue/` | 逾期判定（§14／§16／§17） | 251 件真實逾期決定書，175 件引擎可執行，**167 件可比對者全數與訴願審議委員會一致——該判逾期的沒有漏判**。屆滿日 38 件可比、28 件相符，10 件差異中 7 件為「形式屆滿日 vs 依行政程序法 §48 II 順延後屆滿日」的定義差異 |
| `party/` | **當事人適格（§77-3）——我們現在完全沒做** | 28 件真實不適格案 86% 判對、**0% 誤判成適格**；200 件負樣本 100% 判對 |
| `extractor/` | 規則版欄位抽取 | 合成集 1,607 份 98.3%——**合成集是規則版的主場，不能拿來評估我們的 LLM 版**（來源 README 自述「合成集樂觀估計，真實訴願書會更雜」） |

比對報告見 `docs/2026-09-12-deadline-parity-251.md`。

### 現況的介面

- `backend/nodes/n3_procedure.py` 的 `run()` 呼叫 `backend/engine/deadline.py` 的 `compute()`，回 `Result`
- `screen_art77()` 把期間結果映射成訴願法 §77 各款的篩選
- 系統對 §77 其餘各款標 `not_auto_screened`「屬法律判斷，本系統不自動判定，請承辦人審認」

## User Stories

### US-1: 逾期判定由已驗證的引擎給出，並保留可驗算的算式 [P1]

驗收：
- N3 的逾期判定與 `overdue/rule_engine.py` 的判定**在 251 件測試集上一致**（不一致要逐件說明）
- **算式仍然逐步攤開**——期間引擎是 demo 主秀，「可驗算」那一層不能因為換引擎而消失
- 零 LLM 依賴不變（`run_all.py` 有 ast 遞迴掃描會擋）

**不要直接替換 `deadline.py`。** 來源 README 明說不建議（輸入輸出形狀不同：`TimelinessInput`/`TimelinessResult` vs `compute()`）。先確定要取用哪些**邏輯**，再決定是搬進 `deadline.py` 還是並存。

### US-2: 新增當事人適格判定（§77-3） [P1]

**作為**承辦人，**我想要**系統先幫我檢查訴願人是不是原處分相對人。

驗收：
- `check_standing()` 的三態（適格／不適格／**需人工認定**）如實帶進 payload
- **「需人工認定」必須是一個正當結果，不是失敗**——引擎拿不到「原處分相對人」時就該回它
- §77-3 從 `not_auto_screened` 移出時，要在 payload 說明它現在由規則引擎判定

### US-3: 資料來源的前置確認（阻擋項） [P1]

**這條沒解決，US-2 就做不出價值。**

`party/rule_engine.py` 需要 `respondent_name`（原處分相對人），而**那結構上不在訴願書裡、要從原處分書取得**（來源 README 自己點出的唯一的坑）。

驗收：
- 先確認 N1 的抽取輸入是否包含原處分書
- **若拿不到，US-2 會一路回「需人工認定」，86% 的準確率在我們的 pipeline 裡兌現不了**
- 這條要先查證再實作，**不要做完才發現輸入拿不到**

### US-4: 程序審查結論不再由使用者下拉挑 [P1]

驗收：
- payload 要能讓前端直接得出「程序不合 → 不受理（§77 第幾款）」
- 前端 `ProcPanel.vue` 的 A 選項改由後端結果驅動
- **B（駁回）vs C（撤銷）不在本 change 範圍**——那是實體法律判斷，後端明確拒絕代為認定（C 型封鎖的理由）。本 change **不得**讓它看起來像系統判的

### US-5: 不得把標註資料變成自動判定法律問題的藉口 [P1]

`party/` 有 228 件標好答案的資料。**有了標註資料不會讓法律判斷變成非法律判斷。**

驗收：
- §77 其餘各款維持 `not_auto_screened`
- 該批資料的正當用法是**反向驗證「系統每一件都正確地交給人工」**，不是拿來訓練自動判定

## Edge Cases

| 情境 | 預期行為 |
|---|---|
| 公示送達 | **明示拒絕判定、回 caveat 交人工**——`overdue/` 251 件裡有 7 件是這樣處理的。**拒絕比猜測正確**，這是特性不是缺陷 |
| 送達方式未知 | 同上，不得猜 |
| 拿不到原處分相對人 | §77-3 回「需人工認定」 |
| 屆滿日逢週六日 | 依行政程序法 §48 II 順延。**注意訴願會的決定書記的常是未順延的形式屆滿日**，兩者不是同一個東西，比對時不要當成錯誤 |

## Open Questions

1. **`overdue/` 是搬邏輯進 `deadline.py`，還是並存當第二意見？** 來源 README 建議不直接替換。**並存的好處**是可以做交叉驗證（兩套不一致就標出來給人看），**代價**是維護兩套。
2. **US-3 的原處分書輸入**——這是阻擋項，先查證。
3. 那 10 件屆滿日差異中的 3 件（−3／−6／+9）尚未逐件開卷查證，其中 −3／−6 是「算得太早」的方向，**而 251 件全為逾期案，這批資料測不到「把未逾期誤判為逾期」**。整合後若要宣稱準確率，這個限制要一起講。
