# 三支工具的 prompt 盤點：解析卷證檔案／查找相似案例／搜尋相關法規

> 整理日期 2026-09-13。這份是**現況盤點**，不是規格提案——每一段都註明出處檔案與行號，
> 內容一字未改，照抄自程式。要改 prompt 請改原始檔，然後回來更新這份。

## 一句話總結：三支的「prompt」不是同一種東西

| 工具 | chip | 有沒有 LLM | 所謂的「prompt」實際是什麼 |
|---|---|---|---|
| `extract_case_document` | `/解析卷證檔案` | **有**（N1 呼叫 Bedrock） | 一份真正的 system prompt（`n1_extract.md`）＋ user prompt 模板 ＋ Pydantic schema |
| `search_similar_decisions` | `/查找相似案例` | **沒有**（純向量檢索） | 查詢句的**組法**（由案情欄位串出來）＋ 工具說明 ＋ 回給模型的護欄話術 |
| `search_regulations` | `/搜尋相關法規` | **沒有**（純查表） | 同上 |

後兩支零 LLM 是 `CONSTITUTION.md` §4 的紅線（N2/N3/N4/N6 不得碰模型），由
`backend/tests/run_all.py` 的 `scan_llm_import_graph` 把關。所以它們**沒有 prompt 檔可給**——
真正決定它們查到什麼的是「查詢句怎麼組」，那段放在下面第 2、3 節。

三支共用的對話層 system prompt 是 `backend/llm/prompts/chat_ask.md`（第 4 節）。

## 1. 解析卷證檔案（`extract_case_document`）

- chip 定義：`frontend/src/data/data.js:42`
- 工具說明（模型看到的 docstring）：`backend/llm/chat.py:1727`
- 執行入口：`backend/llm/chat.py:1421` → 跑 N1–N3 流水線
- **system prompt**：`backend/llm/prompts/n1_extract.md`
- user prompt 組法：`backend/llm/client.py` 的 `extract_intake()`
- 輸出 schema：`backend/llm/schemas.py` 的 `ExtractionResult`

### 1.1 system prompt（`backend/llm/prompts/n1_extract.md` 全文）

```markdown
你是新北市政府訴願審議委員會的卷證書記官。你只做一件事：從卷證原文抽出欄位，逐欄附信心值與原文片段。

## 欄位定義

| 欄位 | 是什麼 | 常見的抽錯 |
|---|---|---|
| `no` | **收文案號**——訴願機關收到訴願書後自己編的號，格式像 `1147061234`。若附件檔名就是收文案號，可以用；訴願書內文通常沒有這個號，沒有就 null。 | **不要填原處分字號**（「新北環稽字第○○號」那種）。那是原處分的號，不是收文案號。 |
| `type` | **案件類型**，只能是下面七個字串之一，一字不差：`違反洗錢防制法事件`／`違反廢棄物清理法事件`／`違反空氣污染防制法事件`／`違反噪音管制法事件`／`違反建築法事件`／`申請提供政府資訊事件`／`其他`。依卷證**明寫**的法規名稱對應（例：卷證寫「違反廢棄物清理法相關規定」→ `違反廢棄物清理法事件`）。卷證沒有明寫法規名稱就 null。 | **不要回「訴願」「撤銷」「裁罰（罰鍰）」**——那是案件性質或請求內容，不是案件類型。也不要自創字串。 |
| `person` | 訴願人。法人／公司時填**法人名稱**（例：`○○有限公司`）。 | 法人案不要填代表人姓名。 |
| `org` | 原處分機關（做出原處分的那個機關）。 | — |
| `d1` | **原處分作成日**——處分書的發文日期。 | — |
| `d2` | **合法送達日**——訴願人實際收受原處分的日期。卷證多寫在「收受（知悉）行政處分日期」欄，或書信體的「我在○年○月○日收到」。**卷證沒有這種記載就 null。** | **絕對不要拿 `d1`（處分日）或 `d3`（落款日）充數。**訴願書上有日期不代表那是送達日。 |
| `d3` | **提起訴願日**——訴願書的落款日期／具狀日期，通常在文末。 | 不要跟 `d2` 對調。 |
| `agent` | 代理人（受委任代為提起訴願的人）。 | 法人的**代表人不是代理人**，代表人不要填在這裡。 |
| `note` | 承辦人備註：案情要點、訴願人主張的摘要。 | — |
| `service_method` | 送達方式，見下方規則。 | — |
| `transit_days` | 在途期間天數，見下方規則。 | — |
| `interested_party` | 是否為利害關係人，見下方規則。 | — |

`d1`／`d2`／`d3` 是三個不同的日期：處分「作成」→「送到訴願人手上」→「訴願人提起訴願」。三者常常只有其中一兩個寫在卷證上，**沒寫的那個就是 null**。

## 規則

- 卷證沒寫的欄位，value 給 null、conf 給 0.0，不要猜。**寧可 null，不要填一個看起來合理的值**——填錯的值會被當成已擷取的事實往下游走。
- 日期一律轉成西元 ISO 格式（YYYY-MM-DD）。民國年加 1911。
- service_method 只能是 personal（本人或同居人簽收）、deposit（寄存送達）、public（公示送達）三者之一；卷證沒寫就 null。訴願人**主張**原處分機關如何送達，不等於卷證已載明送達方式——那種情形給 null 或給低 conf。
- transit_days 是在途期間天數（整數），卷證沒寫就 0 且 conf 給 0.5。
- interested_party：訴願人是否為原處分的利害關係人而非相對人；不確定給 false 且 conf 給 0.5。
- respondent_name 是**原處分相對人**（原處分書上的受處分人／受文者姓名或名稱）。這一欄通常只在原處分書裡，訴願書沒有；**卷證裡沒有原處分書就給 null、conf 0.0**。原處分書若以「訴願人」「受處分人」「受文者」等代稱指涉而未寫出姓名，一樣給 null——**代稱不是名字，抄回來會讓當事人適格判錯**。
- facts_excerpt：把「事實」段原文逐字照抄，一段一筆，附頁碼。不要摘要、不要改寫、不要補寫。
- quote 欄位放支撐該值的原文片段，原文照抄。**quote 找不到就代表這一欄該給 null。**
- conf 是「這個值有多可能正確」，不是「我多努力抽了」。從卷證明文照抄的給高分；靠推論得到的給 0.5 以下；卷證沒有依據的一律 null＋0.0。
- 你不做任何法律判斷，不算期間，不判斷是否逾期。
```

### 1.2 user prompt 模板（`backend/llm/client.py`）

```
{若有 PDF 附件，前面加這一行}
若附有 PDF 文件，請直接閱讀其頁面內容（可能是掃描件）。

以下是卷證原文（訴願書全文與原處分書）。請依 schema 抽出欄位。

【訴願書全文】
{document_text}
```

`document_text` 由 N1 把每份卷證串成 `《檔名》\n全文`（`backend/nodes/n1_extract.py`）。
抽不出文字層的 PDF 不走這條，改成 Bedrock 的 `document` content block 直接交給模型讀頁面；
文字部分退成 `（無文字層，請閱讀附件 PDF）`。

### 1.3 模型看得到的工具說明（`backend/llm/chat.py:1727`）

```
解析本案卷證檔案：抽收文欄位、摘錄事實、做程序審查。

**只有卷證還沒解析過、或承辦人明確要求重新解析時才用。**
這一支要跑十秒以上，不要為了確認一件小事就呼叫它。
```

### 1.4 跑完之後餵回給模型的話（不是 prompt 檔，但同樣拘束模型的輸出）

正常：

```
已完成卷證解析（run {run_id}，終態 {state}）。這個 run **只跑到程序審查，沒有草稿**。
```

有節點降級：

```
卷證解析跑完了，但**有節點降級，這個案子還不能往下走**（run {run_id}，終態 {state}）。
降級原因：{stuck}。這個 run 只跑到程序審查，沒有草稿。
請照實把上面的原因告訴使用者，講清楚卡在哪一步、要補哪幾個欄位，並說明補齊後才能續跑。
**不要說解析已完成，也不要說現在可以生成草稿。**
```

失敗：

```
解析卷證失敗（{例外型別}）：{訊息}。請告訴使用者這次解析失敗了，不要編造卷內內容。
```

### 1.5 schema 就是第二道約束

`ExtractionResult` 把十三個欄位收成 `{value, conf, quote}`，文字欄的 `value` 只收
`str | None`（`transit_days`／`interested_party` 例外，保留寬鬆型別＋下游容錯轉換）。
`conf` 限 0–1。**模型想寫的東西沒位置就寫不出來**——這比在 prompt 裡多寫一句禁止更牢靠。

## 2. 查找相似案例（`search_similar_decisions`）

- chip 定義：`frontend/src/data/data.js:46`
- 工具說明：`backend/llm/chat.py:1709`
- chip 路徑執行點：`backend/llm/chat.py:1597` `_search_from_case()`
- 檢索：Bedrock Knowledge Base（`backend/retrieval/kb.py`），**零模型生成**
- 查詢句組法：`backend/nodes/n4_retrieval.py` 的 `build_case_query()`（N4 通道 B 用同一支）

### 2.1 模型看得到的工具說明

```
查性質相近的歷史訴願決定。

Args:
    query: 爭點或處分依據的關鍵字，繁體中文。
```

### 2.2 查詢句怎麼組（chip 按下去時，`query` 從哪來）

chip 不帶查詢詞，而模型**不准自己編一個**（chat_ask.md 紅線 1）。所以缺的那一格由案情確定性補上：

```
case_query = 「；」.join(
    n1.facts_excerpt[].text        # 事實段原文，逐字
  + n1.intake.note                 # N1 寫的案情摘要
  + n2.classification.class.case_type   # 案型
  + 承辦人在「重新檢索」卡指定的補充查詢詞（附在尾端，不取代）
)
```

- **只吃卷證原文＋案型，不吃改寫句**——改寫句實測會漏撤銷案。
- 本案自己要排除（`self_exclusion_keys()`：收文案號、卷證檔名前段），
  否則相似案第一名會是本案自己（2026-09-12 實測 `1141120180` 回自己，相關性 100）。
- 長度上限 900 字（`KB_QUERY_MAX_CHARS`），只在退路上起作用。

### 2.3 導不出查詢詞時回給模型的話

```
這件案子還導不出查詢詞，所以這次**沒有去查**：查詢詞由卷證解析的結果組出來
（案型、程序不受理事由、期間依據的法條），目前這些都還是空的。
請告訴承辦人**要先解析卷證**，跑完之後這個按鈕才查得到東西；
或者他可以直接打字把爭點、處分依據告訴你，你再用那些字去查。
**不要自己想一個查詢詞去查**，也不要說查無相似案例——這次根本還沒查。
```

狀態標 `not_attempted`，**不是** `empty`。「查無」的前提是真的查過了。

### 2.4 查到之後回給模型的話

```
（查詢詞「{節錄}」是系統從本案案情組出來的，來源：{payload 欄位路徑}，
不是承辦人打的，也不是你想的。要講查詢詞就講來源，不要把它整串唸出來。）

[c1] {標題}（{來源}）
{命中段落}
...
```

查無：`相似訴願決定查無結果。請直接說查無，不要引用任何編號。`
失敗：`檢索失敗（{型別}）：{訊息}。請告訴使用者這次查詢失敗了，不要說成資料庫裡沒有這筆資料。`

三種說法必須分得開：**無資料集**（沒有可檢索的庫）／**查無**（查了，回 0 筆）／
**檢索失敗**（查了，呼叫炸了）。混成一種就是對發生過什麼說謊。

## 3. 搜尋相關法規（`search_regulations`）

- chip 定義：`frontend/src/data/data.js:50`
- 工具說明：`backend/llm/chat.py:1700`
- 檢索：`laws-snapshot.json` **查表**（`backend/retrieval/lawtable.py`），零模型生成
- 查詢句組法：`backend/nodes/n4_retrieval.py` 的 `build_query()` / `build_query_sources()`

### 3.1 模型看得到的工具說明

```
查某個法條在不在法規快照裡。**不會回條文原文**，只回存不存在。

Args:
    query: 法規名加條號，例如「訴願法第 14 條」。
```

### 3.2 查詢句怎麼組（每一項都帶自己的出處標籤）

`build_query_sources()` 依序收這幾類，**每一項都記 `from` 與 `kind`**，
拿去跟承辦人說「這串字是從哪來的」：

| 來源 | 是什麼 |
|---|---|
| `n2.classification` | 案型對應的法規名稱 |
| `n3.screen.art77.clause` | 程序不受理事由（款次→只查第 77 條本身） |
| `n3.screen.deadline.steps[].basis` | 期間引擎逐步援引的法源（正規化成「法規名第N條」） |
| `case.documents[].text` | **卷證原文（逐字，未經模型改寫）** |
| `n1.facts_excerpt + intake.note` | N1 整理的摘要與事實段（**note 為模型改寫**，標籤要說實話） |

卷證原文這一項 2026-09-12 才補上，補的是「法規清單時有時無」的 bug：
原本只吃 N1 的摘要，同一份卷證跑兩次，摘要寫法不同就會 laws=1 / laws=0，
**條號一直都在原文裡**，是查詢句看不到它。本案適用哪幾條不該由模型當下的措辭決定。

### 3.3 兩件必須說清楚的事

1. **快照只索引條號，沒有條文原文。** 查得到＝`verified=true`，但 `q`（原文）留空並附說明：
   `條文原文不在快照內（快照只索引條號），本系統不代為補寫條文文字，請對照全國法規資料庫。`
   條文原文另由賽方資料集「相關法規」查表帶出，帶出時標
   `條文原文取自賽方資料集『相關法規』（全國法規資料庫列印版）查表，非模型生成。`
2. **實體法條號不猜。** `SUBSTANTIVE_ARTICLE_UNKNOWN`：N2 只認得出案型對應的法規**名稱**，
   條號要由原處分書的裁處依據判定——所以檢索結果以程序面法條為主，實體面只列得出法規名。

### 3.4 只給純法規名（沒到條）時的話術

```
純法規名查不到。請照實告訴使用者這件事與下一步：要讓某條法規成為草稿的引用依據，
要把它指定到條，例如「訴願法第14條」。不要說它們已被引用，也不要說它們完全沒被用到。
```

## 4. 三支共用的對話層 system prompt

`backend/llm/prompts/chat_ask.md`——承辦人在聊天室追問時，模型帶的就是這一份。
六條紅線與這三支工具直接相關的有四條：

1. **不編造任何字號、案號、函釋編號、判解字號。** 查不到就說查不到。
2. **不計算任何期間、天數、期限或金額**（規則引擎的職責）。
3. **只引用工具真的回給你的東西**，用工具給的 `[c1]`、`[c2]` 編號，不自己發明。
4. **不下法律結論**（訴願有無理由、處分應否撤銷）。

另兩條是講給承辦人聽的話術：不講程式名與內部代號、不描述畫面（你看不到他的螢幕）。
