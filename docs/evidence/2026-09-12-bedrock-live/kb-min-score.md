# KB_MIN_SCORE 量測：0.25 → 0.15，並加上同源 chunk 去重（2026-09-12）

承接 `kb-tuning.md`。那份做完 per-channel over-fetch 與 metadata 側檔之後，
剩下一個沒被量過的參數：`KB_MIN_SCORE=0.25`。這個值從 `.env.example` 第一版就在，
**沒有任何量測依據**。本文是量測結果。

量測腳本：`scripts/measure_kb_min_score.py`（可重跑）。

## 結論先講

**這個門檻不是「調高調低」的問題，是它沒有鑑別力，而且現在這個值正在誤傷。**

| | |
|---|---|
| 對 precision 的貢獻 | **零**（0.15～0.35 之間同案型率都是 96–98%） |
| 對語意無關命中的阻擋力 | **零**（「今天天氣很好」在 0.25 下存活） |
| 對正確命中的誤傷 | **有**（leave-one-out 40 案中 8 案在 0.25 撈不滿 5 筆） |

改為 `0.15`。另外發現同一份文件的多個 chunk 會各自算一筆，一併修掉（見下方第 4 節）。

## 1. A 組：leave-one-out（40 筆公開決定書）

查詢＝該篇決定書內文前 800 字，排除自己，golden＝manifest 的 `category`。

| 門檻 | 撈滿 5 筆的案子 | 平均可用筆數 | top5 同案型率 |
|---|---|---|---|
| 0.15 | 40/40 | 41.6 | 195/200 = 98% |
| 0.20 | 40/40 | 23.1 | 98% |
| **0.25（原值）** | **32/40** | **7.2** | 175/180 = 97% |
| 0.28 | 9/40 | 3.0 | 96% |
| 0.30 | 2/40 | 1.8 | 97% |
| 0.35 | 0/40 | 0.6 | 96% |

**同案型率在所有門檻下紋絲不動。** 門檻不是在篩掉錯的，只是在砍數量。

非自身命中的 score 分布：`max=0.948、p90=0.269、median=0.206、min=0.150`。
0.25 正好切在 p90 附近——換句話說，它砍掉的是九成的正確命中。

> 注意：`category` 只有「廢棄物清理法」1,177 與「空氣污染防制法」1,170 兩類（近 50/50），
> 所以同案型率的隨機基線是 ~50%。98% 遠高於基線，這個指標有效；
> 但它**不足以分辨 0.15 與 0.25 誰比較好**——因為兩者都是 ~97%。真正的差別在筆數。

## 2. C 組：負控制（決定性的一組）

拿語料裡**完全不存在**的案型去查。如果門檻有鑑別力，這些查詢的分數應該明顯低於 A 組。

| 查詢 | max | median | 0.25 下存活 |
|---|---|---|---|
| 訴願人主張系爭商標與據以異議商標構成近似… | 0.5015 | 0.313 | 15/15 |
| 訴願人不服海關就進口貨物完稅價格之核定… | 0.5118 | 0.390 | 14/14 |
| 本件涉及專利申請案之進步性判斷… | 0.4108 | 0.325 | 9/10 |
| **今天天氣很好，我想去公園散步，順便買一杯咖啡。** | **0.7310** | 0.343 | 10/14 |

對照 A 組真實同案型命中的 `median=0.206`：

**閒聊句拿到 0.73，比任何一筆真實的同案型決定書都高。**

原因是 Managed KB 的 score 不是絕對相關度，它對**查詢長度**極度敏感：

- 長查詢（N4 的 `case_query`，數百字）→ 整體壓在 0.15–0.30
- 短查詢（十幾字）→ 輕鬆上 0.3–0.7

N4 的相似案查詢句是整份卷證串起來的長查詢，正好落在被門檻砍的那一段。
所以 0.25 的實際效果是：**放行「今天天氣很好」，擋掉真正的空污案。**

**推論：分數門檻無法承擔「擋掉語意無關命中」這個任務，該由 metadata filter 承擔。**
（側檔的 `category` 已經在 KB 裡了，`kb-tuning.md` 做的；接上 filter 是後續項。）

## 3. B 組：改動前後的真實 case_query 對照

`synthetic-ordinary-01`（demo 案），相似案通道 `overfetch=3`：

| min_score | 筆數 | 相異檔案 |
|---|---|---|
| 0.25 | 5 | 5 |
| 0.15 | 5 | 5 |

**demo 案的畫面結果完全不變。** 這不是巧合：`kb.py` 是按 score 降序過濾後取前 `top_k`，
所以降門檻**對已經撈滿 5 筆的案子零影響**，只會救那些撈不滿的（A 組的 8/40）。
這個改動是純增益。

## 4. 附帶發現：同一份文件的多個 chunk 各自算一筆

量測時發現的，跟門檻無關但更嚴重。

查詢「寄存送達 自寄存之日起發生效力」回的 3 筆函釋：

```
0.955  行政函釋/法務部93年4月13日法律字0930014628號函-寄存送達.txt
0.445  行政函釋/法務部93年4月13日法律字0930014628號函-寄存送達.txt
0.283  行政函釋/法務部93年4月13日法律字0930014628號函-寄存送達.txt
```

**同一個檔案的三個 chunk。** `kb-tuning.md` 記的「`retrieve_refs` 要 5 筆只拿得到 3 筆」，
實際是「只拿得到 **1 份**」——比當時判斷的更嚴重，而且跟 `REF_OVERFETCH=10` 撒大網無關，
網再大也還是同一份的切片。

相似案通道同樣會中：`synthetic-ordinary-01` 改動前的 5 筆裡，
`03.113年-違反空氣汙染防制法事件-77(2)-訴願逾期-不受理.txt` 出現兩次（0.5630／0.5604）——
**承辦人看到 5 張相似案卡，其實只有 4 件案子。**

承辦人看到「3 筆依據」而實際只有 1 份，是對「有多少佐證」說謊（CONSTITUTION §1）。
`kb.py` 加 `seen_sources` 去重，一份文件只留最高分的那個 chunk
（`retrieve` 已按 score 降序，first-seen 即最高分）。

## 6. 量測期間查出來的既有問題（非本次改動造成）

`live_acceptance.py` 目前有 5 條 ❌：AC10、AC7、AC8b、AC6、AC15。
**在本次改動之前就是這樣**（新舊程式碼各跑一次，結果逐條相同）。

其中 AC10／AC7／AC6／AC15 是同一個根：

```
state: NEEDS_INPUT
events: ['node_start', 'node_done', 'run_done']     ← 只有一對，不是六對
classification: {}
```

`POST /api/cases/{id}/runs` 送空 body 時，流程跑完 N1 就停在 `NEEDS_INPUT`
等人確認收文欄位（commit 31b3486「N1 停止（NEEDS_INPUT）看板」引入的行為）。
**N2–N6 根本沒跑**，所以：

| AC | 表面症狀 | 真正原因 |
|---|---|---|
| AC10 | SSE 只有 1 對 start/done | 只跑了 N1 |
| AC7 | `cases=0` | N4 沒跑，不是 KB 回 0 筆 |
| AC6 | `requires_human_conclusion=False` | N3 沒跑 |
| AC15 | `KeyError: 'class'` | N2 沒跑，`classification` 是空 dict |

**驗收腳本沒有跟上 N1 NEEDS_INPUT 的行為改變**：它假設一次 POST 就跑完六節點，
而現在那需要先確認 intake。證據是同一支腳本的 AC9（明確帶 `confirmed_intake` +
`from_node=n2`）是 ✅，且手動走那條路徑 AC7 也是 ✅（見上節）。

修法（本次未做）：AC7／AC6／AC10／AC15 的 payload 應改從「確認後續跑」那次取，
像 AC9 一樣帶 `confirmed_intake`；或是讓第一條「跑完六節點」真的去驗節點數——
它現在只看 HTTP 200 與 `run_mode`，名稱與實際檢查不符，這正是它沒能把問題擋下來的原因。

AC8b（`from_node` 無 `base_run_id` 應回 400，實際回 202）是另一件事，未查。

   attribute filter（`kb.py` 現有註解只說了路徑比對不支援，attribute 未測）。
